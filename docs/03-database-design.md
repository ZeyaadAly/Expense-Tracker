## 1. Design overview

Use Supabase PostgreSQL with one application table: `expense_tracker.transactions`. Each row represents one income or expense transaction. Express is the only application component that accesses transaction data.

V1 has one shared transaction collection and no authentication or user ownership column. Adding accounts later requires an ownership-aware migration and access policy first. Categories are fixed values enforced by constraints; a separate categories table is unnecessary until category management is introduced.

Use a dedicated `expense_tracker` schema and fully qualified table names in Supabase PostgreSQL. The remote V1 schema already exists. Pull it with the Supabase CLI to create the authoritative baseline migration; do not execute this document's reference SQL against the remote project again.

## 2. Table definition

| Column | PostgreSQL type | Required/default | Purpose |
| --- | --- | --- | --- |
| `id` | `uuid` | Primary key; generated by Express | Unique transaction identifier; never editable through the API. |
| `type` | `text` | Required | `income` or `expense`; API/UI labels map to Income and Expense. |
| `amount` | `numeric` | Required | Exact positive amount in EGP, with explicit range and decimal-place checks. |
| `description` | `text` | Required | Trimmed plain text, 1–200 Unicode code points. |
| `category` | `text` | Required | Lowercase category code valid for the selected type. |
| `transaction_date` | `date` | Required | Date on which the transaction occurred; no time component. |
| `created_at` | `timestamptz` | Database-generated | Creation instant; preserved on update. |
| `updated_at` | `timestamptz` | Database-generated | Most recent insert/update instant. |

Express generates `id` using a UUID generator before insertion. It accepts only the five user-editable fields and excludes supplied identifiers/timestamps from writes.

`timestamptz` represents an instant. Return timestamps as ISO 8601 strings in UTC. Keep `transaction_date` as a `YYYY-MM-DD` string throughout database-driver and API handling; do not convert it to a JavaScript Date and shift it across timezones.

## 3. Exact money representation

Use unconstrained `numeric` with explicit checks for the amount range and `scale(amount) <= 2`. PostgreSQL numeric arithmetic is exact for addition and subtraction. A declared scale such as `numeric(11,2)` would round excess decimal places before a column check can reject them, which conflicts with our requirements.

- Allowed range: 0.01 through 999,999,999.99 EGP.
- Keep monetary request/response values as decimal strings, such as `"250.50"`.
- Express validates the original amount string before sending it as a query parameter. Reject exponent notation, currency symbols, separators, and more than two fractional digits.
- A suitable canonical input format is `^(0|[1-9][0-9]{0,8})(\.[0-9]{1,2})?$`, followed by an exact range check. This also rejects unnecessary leading zeros.
- Normalize valid values by string operations to two decimals, without converting through JavaScript floating-point numbers.
- Preserve PostgreSQL numeric results as strings. Format summary strings to two decimals without casting totals to a transaction-sized numeric type.
- Calculate totals in PostgreSQL; do not add monetary values with JavaScript Number.

Database constraints protect numeric values. They cannot recover original textual syntax once PostgreSQL has converted a value, so Express must enforce the request format too.

## 4. Category codes

| Type code | Allowed category codes | UI labels |
| --- | --- | --- |
| `income` | `salary`, `freelance`, `gift`, `other` | Salary, Freelance, Gift, Other |
| `expense` | `food`, `transport`, `shopping`, `bills`, `entertainment`, `other` | Food, Transport, Shopping, Bills, Entertainment, Other |

Store codes consistently in lowercase. The interface displays friendly labels. The database rejects category/type combinations that do not appear in this table.

## 5. Validation responsibilities

| Rule | Express responsibility | Database protection |
| --- | --- | --- |
| Required fields | Return useful field errors | `NOT NULL` |
| Type/category | Validate supported codes and pair | Type and category check constraints |
| Amount | Validate original decimal string and exact range | Numeric range and scale checks |
| Description | Trim JavaScript whitespace; count Unicode code points | Reject surrounding whitespace and enforce length |
| Date | Validate strict format, real calendar date, and Cairo boundary | `date`, static lower-bound check, and write-time future-date trigger |
| ID/timestamps | Generate ID; ignore no user-managed metadata—reject these input fields in API design | Primary key; database timestamp trigger |

The 200-character limit counts Unicode code points, consistent with PostgreSQL `char_length`. JavaScript's default string length counts UTF-16 units; implementation must use a code-point-aware count.

Future-date validation uses a trigger rather than a check constraint involving the current clock. Check constraints should express conditions that remain stable for a stored row. The database trigger checks the current Cairo date at write time; Express applies the same rule independently.

## 6. Proposed schema SQL

This SQL records the design intent for comparison with the existing remote schema. The Supabase CLI pull, once completed and reviewed, is the authoritative baseline migration. Do not run this reference SQL against the remote project again.

```sql
BEGIN;

CREATE SCHEMA expense_tracker;

CREATE TABLE expense_tracker.transactions (
    id uuid PRIMARY KEY,
    type text NOT NULL,
    amount numeric NOT NULL,
    description text NOT NULL,
    category text NOT NULL,
    transaction_date date NOT NULL,
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    updated_at timestamptz NOT NULL DEFAULT statement_timestamp(),

    CONSTRAINT transactions_type_check
        CHECK (type IN ('income', 'expense')),
    CONSTRAINT transactions_amount_range_check
        CHECK (amount >= 0.01 AND amount <= 999999999.99),
    CONSTRAINT transactions_amount_scale_check
        CHECK (scale(amount) <= 2),
    CONSTRAINT transactions_description_check
        CHECK (
            char_length(description) BETWEEN 1 AND 200
            AND description !~ '^[[:space:]]'
            AND description !~ '[[:space:]]$'
        ),
    CONSTRAINT transactions_category_check
        CHECK (
            (type = 'income' AND category IN
                ('salary', 'freelance', 'gift', 'other'))
            OR
            (type = 'expense' AND category IN
                ('food', 'transport', 'shopping', 'bills',
                 'entertainment', 'other'))
        ),
    CONSTRAINT transactions_date_min_check
        CHECK (transaction_date >= DATE '1900-01-01')
);

CREATE FUNCTION expense_tracker.validate_transaction_write()
RETURNS trigger
LANGUAGE plpgsql
SECURITY INVOKER
SET search_path = pg_catalog
AS $$
BEGIN
    IF NEW.transaction_date >
        (statement_timestamp() AT TIME ZONE 'Africa/Cairo')::date THEN
        RAISE EXCEPTION 'Transaction date cannot be in the future'
            USING ERRCODE = '23514';
    END IF;

    IF TG_OP = 'INSERT' THEN
        NEW.created_at := statement_timestamp();
    ELSE
        IF NEW.id IS DISTINCT FROM OLD.id THEN
            RAISE EXCEPTION 'Transaction identifier cannot be changed'
                USING ERRCODE = '23514';
        END IF;
        NEW.created_at := OLD.created_at;
    END IF;
    NEW.updated_at := statement_timestamp();
    RETURN NEW;
END;
$$;

CREATE TRIGGER transactions_validate_write
BEFORE INSERT OR UPDATE ON expense_tracker.transactions
FOR EACH ROW
EXECUTE FUNCTION expense_tracker.validate_transaction_write();

CREATE INDEX transactions_order_idx
ON expense_tracker.transactions
    (transaction_date DESC, created_at DESC, id DESC);

REVOKE ALL ON SCHEMA expense_tracker FROM PUBLIC;
REVOKE ALL ON TABLE expense_tracker.transactions FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION
    expense_tracker.validate_transaction_write() FROM PUBLIC;

COMMIT;
```

Database whitespace classification depends on locale and is not a replacement for Express trimming. Express normalizes descriptions before storage, including Unicode whitespace.

The bounded range check also excludes PostgreSQL special numeric values such as NaN and infinity. Future-date checks reject an infinite future date; the minimum-date check rejects an infinite past date.

## 7. Query patterns

### List transactions

```sql
SELECT id, type, amount::text AS amount, description, category,
       to_char(transaction_date, 'YYYY-MM-DD') AS transaction_date,
       created_at, updated_at
FROM expense_tracker.transactions
ORDER BY transaction_date DESC, created_at DESC, id DESC;
```

Build optional filters from fixed SQL fragments and parameterize their values:

- Type filter: `WHERE type = $1`.
- Category filter: `WHERE category = $1`.
- Combined filters: `WHERE type = $1 AND category = $2`.
- Omit filters entirely for All; do not store `all` as a category or type.

Keep the same ordering for every filter combination. The order index supports the default list. For a small V1 table, avoid extra low-selectivity type/category indexes until query plans and actual data volume show a need.

### Overall financial summary

```sql
WITH totals AS (
    SELECT
        COALESCE(SUM(amount) FILTER (WHERE type = 'income'), 0::numeric)
            AS total_income,
        COALESCE(SUM(amount) FILTER (WHERE type = 'expense'), 0::numeric)
            AS total_expenses
    FROM expense_tracker.transactions
)
SELECT total_income::text AS total_income,
       total_expenses::text AS total_expenses,
       (total_income - total_expenses)::text AS balance
FROM totals;
```

Do not add list filters to the summary query. Totals may exceed the maximum amount of an individual transaction. Do not store totals in another table; deriving them avoids stale balances.

### Create, update, and delete

- Use parameterized `INSERT ... RETURNING`, `UPDATE ... WHERE id = $n RETURNING`, and `DELETE ... WHERE id = $1 RETURNING id` statements.
- Update all five editable fields together using validated input.
- Zero returned rows on update/delete means the record was not found.
- A single statement is atomic. Use an explicit transaction if a future operation requires several dependent writes.
- Return success only after the write has committed. Reload the list and summary afterward.
- V1 uses last-write-wins for simultaneous edits; optimistic concurrency control is deferred.

## 8. Connection and access design

Use one reusable connection pool in Express with a server-only `DATABASE_URL`. Select pool size and provider connection mode during setup based on documented limits and the backend runtime. Use provider-required TLS settings and do not disable certificate checks as a workaround.

Separate migration access from application access. The application role needs schema usage and transaction-table SELECT, INSERT, UPDATE, and DELETE privileges; it does not need permission to create/drop tables or manage roles. Configure the trigger function's execution grants as part of the migration-role setup.

Keep `expense_tracker` outside Data API exposed schemas and verify that `anon` and `authenticated` have no access to it. Do not add the schema to the exposed list or create public access policies to solve connection errors. V1 has no user ownership model; the limited PostgreSQL role and Express API are the intended access path.

The frontend does not use a Supabase client or access this database schema directly. Express uses only `DATABASE_URL` for database access. Because V1 is unauthenticated, use sample data for any hosted demo.
